# OCR engine A/B — Unlimited-OCR vs gemma4 vision (2026-07-27)

**Unlimited-OCR is 12× faster and 4× more accurate than the default LLM, at the same time.**

| | gemma4:12b-it-qat (vision) | **baidu/Unlimited-OCR Q4_K_M** |
|---|---:|---:|
| overall CER | 10.77 % | **2.71 %** |
| latency | 13.0 s/page | **1.1 s/page** |
| perfect pages | 29 / 105 | **59 / 105** |
| failures | 0 | 0 |
| VRAM | 7.6 GB (already resident) | 1.95 GB + 0.83 GB mmproj |
| params | 12 B dense | 3 B total / **0.57 B activated** (MoE) |

## Method

- **Corpus** `D:/TerranSoul/jd-1000-scanned` — 1,000 image-only PDFs generated by
  `npm run ocr:build-scanned`. Verified text-layer-free (no `/BaseFont`, no `BT..Tj`, images only),
  so OCR genuinely runs; a text-layer PDF would be extracted directly and measure nothing.
- **Ground truth is exact, not transcribed.** Résumé N is a pure function of `(seed, N)`, so the
  reference text is known byte-for-byte and CER is exact rather than approximate.
- **Slice** 105 pages, `--stratify` (15 per language × 7). A head slice would over-represent
  whichever language leads the interleave, and CER is reported per language.
- **Degradation** `medium` — 200 DPI, greyscale, 0.8° rotation, 0.6 blur, noise, JPEG q72. A pristine
  render is not a scan and would not discriminate engines.
- **Scoring** `npm run ocr:score` — CER weighted by reference length, NFC-normalised (without which a
  correct Vietnamese transcription can score arbitrarily badly), whitespace collapsed. WER only for
  space-delimited languages. Missing pages are reported, never scored as perfect.

## Two harness defects that would have produced a wrong answer

1. **Unlimited-OCR does not emit plain text.** It emits an OmniDocBench-style parse —
   `title [93, 53, 372, 76]Patricia Anderson`. Scoring that raw counts every coordinate as a
   character error. `stripLayoutAnnotations()` removes exactly that prefix shape and nothing else.
2. **The first run was silently on CPU** and measured 13.1 s/page — indistinguishable from gemma4,
   which would have killed the whole proposal. The b10144 zip ships binaries only; llama.cpp needs
   the **separate cudart zip** or it falls back to CPU without saying so. With CUDA the same work is
   1.1 s/page. **Any llama.cpp latency number taken without confirming GPU offload is worthless.**

## Reproduce

```bash
npm run ocr:build-scanned -- --count 1000 --out D:/TerranSoul/jd-1000-scanned --degrade medium
# llama-server -m unlimited-ocr-Q4_K_M.gguf --mmproj unlimited-ocr-mmproj-f16.gguf --port 8085 -ngl 99
npm run ocr:run -- --corpus D:/TerranSoul/jd-1000-scanned --out hyp.jsonl \
  --engine unlimited --model unlimited-ocr --limit 105 --stratify
npm run ocr:score -- --truth D:/TerranSoul/jd-1000-scanned/manifest.jsonl --hyp hyp.jsonl
```

## Caveats, stated rather than buried

- **Korean is not solved.** 17.10 % CER is the one language where Unlimited-OCR does not win
  decisively, and it is worse than its own Chinese by ~570×. Worth a targeted look before claiming
  blanket multilingual superiority.
- **105 pages, not 1,000.** Per language n=15. The full 1,000-page run is now cheap at 1.1 s/page
  (~18 min) and should be done before publishing.
- **The paper's own headline numbers are inflated** and we should not repeat them: its "+6.22" on
  OmniDocBench v1.5 is measured against its older sibling (87.01), while the best baseline in its own
  Table 1 is DeepSeek-OCR 2 at 89.17 — an honest +4.06. Its v1.6 "SOTA 93.92" is a +0.02 lead over
  Qianfan-OCR. **The numbers above are ours, measured on our corpus, and do not depend on either.**
