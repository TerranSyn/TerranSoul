# ADR 006 — VRM avatar, motion tokens, and streaming tag pipeline

**Status:** Accepted  
**Date:** 2025–2026  
**Source:** `src/renderer/`, `src-tauri/src/animation/`, `src-tauri/src/persona/`

---

## Context

A desktop AI companion needs a character body — not just a chat bubble.
Three distinct problems need to be solved together:

1. **Avatar rendering** — display a 3D VRM model in real time.
2. **Motion generation** — the LLM output must drive the avatar's pose and expression.
3. **Live motion capture** — the user can drive the avatar themselves (VTuber mode).

These problems interact: the LLM stream, the pre-authored animation library,
and the live webcam input all compete for the same VRM rig at 60 fps.

## Decision

A **layered animation system** where sources are prioritised by a blending stack,
and the LLM generates motion as discrete **tokens** extracted from its text stream.

---

## Three-layer blending stack (highest priority wins)

```
┌─────────────────────────────┐  Priority
│ 1. VTuber live capture      │  Highest — real-time webcam → Kalidokit → bones
│    (when vtuber_mode on)    │
├─────────────────────────────┤
│ 2. VRMA / learned animation │  Mid — baked VRMA clip or codebook motion token
│    (mood-triggered or LLM)  │
├─────────────────────────────┤
│ 3. Procedural idle          │  Lowest — CharacterAnimator: breathing, sway,
│    + LLM pose additive      │           LLM Euler offsets blended additively
└─────────────────────────────┘
```

Higher layers "yield" when they finish; the stack falls back to the next layer.
A VRMA clip ends → the procedural idle resumes. VTuber mode off → procedural idle.

---

## LLM motion via streaming tag parser

The LLM doesn't just output text — it outputs a dual stream:

```
<thinking>I'll greet the user warmly</thinking>
Hello! How are you doing?
<anim>{"emotion":"happy","motion":"wave"}</anim>
```

The Rust `StreamTagParser` (`src-tauri/src/commands/streaming.rs`) extracts
these tags in real time from the LLM NDJSON stream **before** the text reaches the
frontend. The `motion` value is a **motion token**: a short string key that maps to
a playable VRMA file in the animation library.

### Motion token lifecycle

```
LLM outputs "wave"
  → StreamTagParser extracts anim block
  → Frontend receives "motion:wave" event
  → VrmaManager looks up motion_token → .vrma path
  → Three.js mixer plays the clip
  → On clip end, procedural idle resumes
```

Tokens are generated by:
- The active LLM (from charisma teaching context)
- Manual authoring in the Animation Studio
- VTuber live capture sessions (`animation_batch_learn_vtuber`)

The mapping from token → VRMA lives in the animation store (SQLite), not hardcoded.
Adding a new motion requires one `animation_create` call, not a code change.

## VRM avatar pipeline

| Component | Implementation | Purpose |
|-----------|---------------|---------|
| Avatar loading | `@pixiv/three-vrm` | VRM 0.x + 1.0 humanoid loading in Three.js |
| Animation playback | `@pixiv/three-vrm-animation` | VRMA clip playing via Three.js `AnimationMixer` |
| LLM pose blending | `PoseAnimator` (`src/renderer/pose-animator.ts`) | Additive Euler-angle offsets from LLM stream, cross-faded with spring damping |
| Face mirroring | `src/renderer/face-mirror.ts` | ARKit-style blendshapes from webcam, mapped to VRM expressions |
| VTuber live rig | `src/renderer/vtuber-capture.ts` | MediaPipe PoseLandmarker + FaceLandmarker → Kalidokit → VRM bones |
| Inverse kinematics | `src-tauri/src/animation/ik/` | FABRIK solver for leg/foot grounding |
| Motion tokens | `src-tauri/src/persona/motion_tokens.rs` | Discrete motion vocabulary stored in brain |

## Why VRM over Live2D

| Factor | VRM | Live2D |
|--------|-----|--------|
| Open format | Yes (VRM Consortium) | No (Cubism SDK, proprietary) |
| 3D (full body) | Yes | 2D sprite with depth tricks |
| Import from Vroid Hub | Yes | No |
| Commercial use | Open spec, free runtime | Cubism SDK has commercial licensing fees |
| Three.js integration | `@pixiv/three-vrm` (MIT) | Cubism Web SDK (proprietary) |

VRM is the de-facto standard for VTuber-style 3D avatars. Live2D was evaluated
and explicitly rejected — see `docs/licensing-audit.md`.

---

## Why motion tokens over direct keyframe generation

The LLM could output full bone keyframe data, but:
- A single frame is ~11 bones × 4 floats = 44 floats — verbose for a text stream.
- The LLM would need to generate physically plausible motion — beyond its training.
- Motion library clips are authored, polished, and user-customizable.

Tokens (`"wave"`, `"shrug"`, `"nod"`) are short, semantically meaningful, and
map to the full richness of a pre-authored VRMA clip. The LLM chooses *what*
to do; the animation library decides *how* to do it perfectly.

---

## Consequences

**Good:**
- New motions are added to the library without code changes.
- The LLM output drives genuine 3D body language, not just face expressions.
- VTuber mode reuses the same bone path as LLM-driven motion — no parallel stacks.

**Trade-offs:**
- StreamTagParser must be resilient to LLM outputs that are partially malformed XML.
  (Handled by `malformed_tag_errors` tracking and instructional feedback on the
  next turn.)
- VRMA files are stored in the app data directory, not bundled — first-run requires
  downloading the base motion pack.
